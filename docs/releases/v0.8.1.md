# v0.8.1 corrective release — prepared, not published

## Why this release is needed

Published v0.8.0 points to `6e8a280`, the same source commit as v0.7.0. Its
binaries report 0.8.0 but omit the attestation and chain commands described in
later documentation. v0.8.1 must be tagged from the reviewed merged commit that
contains these implementations, regression fixtures, and release checks.
Do not move or replace published v0.7.0 or v0.8.0 tags.

## Changes to announce

- Configuration attestation with embedded Claude Code and Codex capture contracts,
  requirement results, a foreground watcher, and retained observation history.
- Configuration results in CLI reports and the local dashboard.
- Experimental prompt/edit/finding reports and optional SaaS seals. Commit links
  are path-based associations, not verified edit-to-commit attribution.
- Updated dashboard branding and documentation.
- Regression fixtures maintained independently of demo recordings.
- Release and CI checks for documented command syntax and embedded contracts.

## Upgrade notes

After the release is available, install it, confirm `secuarden version`, inspect
`secuarden attestation contracts`, and refresh hooks using that installed binary.
Use a fresh session to verify live delivery. Existing explicit attestation disables
are preserved. Configuration checks do not establish runtime delivery.

Local hashes cannot prove complete capture or prevent a machine owner from
rewriting records. `verify` does not cover the separate edit-revision/finding
tables or prove commit attribution. SaaS sealing requires a compatible service;
its deployed behavior has not been accepted as part of this preparation.

## Publication checklist — approval required

1. Review preparation changes and their validation results. Obtain approval before
   pushing, merging, changing the live site, or creating a release tag.
2. Merge the reviewed preparation and wait for CI to pass on that exact commit.
3. Verify the intended commit contains `cmd/attestation.go`, `cmd/chain.go`, and
   `scripts/check-release-commands.py`. Record its full SHA; do not tag an old local
   branch merely because its name is main.
4. Create v0.8.1 against that explicit reviewed SHA and push only that tag.
5. Check the release workflow and checksums. Download the actual published binary
   and rerun `scripts/check-release-commands.py` against it before describing the
   docs as release-validated. Perform fresh live-agent acceptance separately.
6. After artifact validation and approval, update the site compatibility table and
   candidate banners to v0.8.1 availability. Search indexing remains a separate
   publication choice; keep noindex until approved.

These steps are preparation only; no tag, release, or site publication is implied.
